# ADR-020: The upgrade authority leaves CI

## Context

ADR-011 put the trust model on a ladder — `0.x` a single key on devnet, `1.0.0-beta` a Squads
3-of-5 with a time lock, `1.0.0` renounced — and said the program id keypair would be
*"generated offline, held by the multisig custodians"*. The first rung was reached on
2026-09-20 in the way first rungs usually are: with whatever key was at hand.

That key is `5eznzq18xdeVaagEkyo7DYb8v12mAWmYcz6AdWTnH8JQ`. Reading its devnet history back,
it has done three unrelated jobs since it was funded with 5 SOL on 2026-09-17:

- it is the **upgrade authority** of `4qjD6vSgYa3oBKde3KVzsH8oCcP9BKsirX1xtD5SS6BS`, having
  deployed it across 696 transactions;
- it is the value of the **`DEVNET_KEYPAIR` GitHub Actions secret**, which the nightly e2e
  preflight and the release-tag smoke both read;
- it is the **owner** of the demonstration treasuries that exist on devnet.

The first two are the problem, and the problem is not the balance. Whoever reads that
repository secret does not merely gain 1.33 devnet SOL; they gain the ability to replace the
program underneath every treasury that trusts it — including, once a treasury holds anything
a person cares about, the ability to replace the code that decides whether a payment is
allowed. Two blast radii several orders of magnitude apart sit behind one secret, and nothing
about the current setup makes that visible to anyone reading the repository.

Four things constrain the answer.

**The program id is load-bearing.** `declare_id!`, `Anchor.toml`, the committed IDL and every
file generated from it name `4qjD6…`. Changing it is not a governance action; it is a
migration, and ADR-011 scopes migrations to `2.x`.

**No CI job needs the authority.** `release-tag.yml` builds, hashes and pays for the devnet
smoke; `e2e.yml` reads the key's balance as a preflight. Neither upgrades anything. What CI
needs is a funded wallet, which is a much smaller thing than what it currently has.

**The multisig is a mainnet commitment.** ADR-011 scopes Squads 3-of-5, the time lock and the
72-hour notice to `1.0.0-beta`. Standing one up on devnet now is ceremony that protects a
program nobody has funds behind, and it would train everyone involved to click through
approvals that carry no weight.

**An agent cannot do this.** `.claude/hooks/guard.sh` denies `solana program deploy`,
`write-buffer`, `close` and `set-upgrade-authority` outright, with the reason attached: *"no
CI step sits between this command and a program holding custody. The owner runs it."* That
rule already encodes the conclusion below; this ADR is the rest of it.

## Options considered

**A. Leave it.** Free, and defensible for exactly as long as devnet holds nothing. It fails
the first question a reviewer asks about the trust model, and the answer — "the CI secret can
replace the program" — is worse than the reality, because the reality is just that nobody got
around to separating them.

**B. Renounce now.** Set the authority to `None`. The strongest claim available, and the wrong
one at `0.x`: the program is unaudited, `packages/cli` is still growing instructions against
it, and an unaudited program that cannot be fixed is not a safety property. ADR-011 already
schedules this for `1.0.0`, after the audit.

**C. Squads 3-of-5 on devnet now.** Faithful to the shape of the endpoint, and premature. It
puts three people in the loop for a devnet redeploy that happens during development, which
means the loop gets bypassed.

**D. A separate offline key, held by the owner; CI keeps only a funded wallet.** One
transaction, no code change, and it removes the escalation from the secret without pretending
to be the multisig.

## Decision

Option D.

**The new authority is generated by the person who will hold it,** outside the repository,
with the seed phrase written down offline. It never enters a GitHub secret, never enters
`.agent-rails/`, and never becomes a CI variable. If it ever appears in any of those places,
this decision has been undone and the repository is back where it started.

**The transfer uses the checked instruction.** `solana program set-upgrade-authority` is given
the new authority's *keypair file*, so both keys sign and the loader's `SetAuthorityChecked`
path runs. `--skip-new-upgrade-authority-signer-check` is forbidden here: it accepts a bare
pubkey, and a typo in that argument transfers the authority to an address nobody holds and
freezes the program permanently. The saving is one signature; the downside is unrecoverable.

**The CI key keeps one job.** After the transfer it pays for the devnet smoke and satisfies
the e2e preflight. It remains the owner of the throwaway treasuries the smoke creates, which
is correct — each run creates its own and nothing of value accumulates in them. The treasury
shown in a demo is a different matter: it must be owned by a key a person holds, not by a
repository secret.

**The claim is checkable rather than asserted.** `agent-rails doctor` reads the authority out
of the loader's `ProgramData` account and prints it, saying so out loud when it matches the
wallet running the command
(`packages/cli/src/chain/upgrade-authority.ts`). The README's trust-phase table points at that
command instead of restating a value that would go stale the moment it changed. This closes a
gap ADR-011 opened: it promised `doctor` would report the authority state, and until now
`doctor` never looked.

**Rotation and loss are different events.** A suspected compromise is another transfer, from
the current authority to a fresh one, and costs a transaction. A *lost* authority key is not
recoverable: the program stays at the bytes it currently holds, forever, and the only way
forward is a new program id — `declare_id!`, `Anchor.toml`, the IDL, the generated client, a
redeploy at ~3.55 SOL of programdata rent, and every manifest that names the old id. That is
ADR-011's `2.x` path walked for a bad reason, and it is why the backup is part of the decision
rather than an operational detail.

## Consequences

The devnet program becomes un-upgradeable from CI, which is the point. Any redeploy is a
deliberate act by a person at a terminal with a key that lives nowhere else — the same posture
the guard hook already enforces against agents, now true of the automation as well.

There is one more key that must not be lost, and its loss is expensive in a way that a lost CI
key is not. The cost is written out above so that nobody has to rediscover it during an
incident.

This does not satisfy ADR-011 point 1. The authority is still a single developer key, not the
`rail…` vanity id held by custodians, and the README's `0.x` row still says a single key can
replace the program. What changes is that the key is *one* power in *one* place, held by a
person rather than by a CI provider's secret store.

It is the cheapest rung on ADR-011's ladder and it should not be mistaken for the top of it.
The multisig, the time lock and the notice window remain mainnet commitments, unimplemented,
and this ADR does not advance them.
